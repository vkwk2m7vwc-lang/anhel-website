# ANHEL — Технический аудит «под капотом»

Цель: найти и устранить технический долг, проблемы производительности, утечки и грязь, накопившиеся за последние недели разработки. Внешний контур (UI, дизайн, тексты) НЕ трогаем — это будет отдельной задачей.

Жалоба пользователя: «стало тяжело открываться, тяжело» — главный приоритет производительность.

---

## ПОРЯДОК РАБОТЫ

1. **Разведка перед правками.** Прогоняешь все блоки чек-листа, собираешь метрики, готовишь отчёт-таблицу с приоритизацией.
2. **Согласование плана.** Присылаешь отчёт мне → я выбираю ТОП проблем для немедленного фикса.
3. **Правки.** Только после моего «ок». Атомарные коммиты по группам, отдельная ветка `chore/internal-audit`.
4. **Перепрогон метрик.** После правок — повторный замер, что улучшилось.

Не исправляй ничего на этапе разведки. Только собирай данные.

---

## РАЗДЕЛ 1. РАЗМЕРЫ И БАНДЛЫ

Проверь то, что грузится в браузер пользователя — это первая причина «тяжело».

- `npm run build` — запусти, дождись отчёта Next.js. Зафиксируй размеры всех маршрутов: «Size» и «First Load JS».
- Маршруты с **First Load JS > 200 KB** — в красную зону. Указать какие.
- `next-bundle-analyzer` — установи временно, прогони, найди топ-10 самых жирных импортов. Часто виноваты:
  - вся `lucide-react` импортируется целиком вместо нужных иконок
  - `framer-motion`, `gsap`, `three.js` грузятся на страницы где не используются
  - `recharts` / `d3` подключены глобально
  - `tailwind-merge` или `clsx` многократно дублируются
- Дубликаты зависимостей в `package.json` — `npm ls` покажет если какая-то библиотека ставится в нескольких версиях.
- Размеры публичных ассетов (`public/`) — найди файлы тяжелее 1 МБ. PNG которые должны быть WebP. Видео без сжатия.

## РАЗДЕЛ 2. КАРТИНКИ И МЕДИА

Это вторая частая причина «тяжело».

- `public/` — есть ли PNG где должен быть WebP. Особенно для hero и галерей.
- Используется ли `next/image` везде где есть `<img>`. Поиск по коду `<img` без `next/image`.
- Есть ли LCP-изображение с атрибутом `priority` на главной и продуктовых страницах.
- У всех `<Image>` есть `width` / `height` или `fill` с `sizes`. Без этого — CLS.
- Картинки в `public/assets/products/` — проверь размеры. 1400px по длинной стороне — ок. Больше 2000px — пересжать.

## РАЗДЕЛ 3. ШРИФТЫ

- `next/font` используется ли вообще, или шрифты грузятся через `<link rel="stylesheet">` с гугла. Гугл-шрифты напрямую = +200-400 ms TTFB.
- Сколько весов шрифтов реально подключено. Часто грузится 5 весов когда нужно 2.
- `font-display: swap` или `optional` — должно быть.
- Самохостинг шрифтов через `next/font/local` лучше чем `next/font/google`.

## РАЗДЕЛ 4. КЛИЕНТСКИЕ КОМПОНЕНТЫ

В Next.js 14 App Router — каждый `'use client'` компонент тянет за собой JS в браузер. Это главный пожиратель производительности.

- Поиск всех файлов с `'use client'`. Список с путями.
- Для каждого ответь: точно ли клиентский? Часто `'use client'` ставят бездумно.
- Можно ли часть логики вынести в Server Component. Например, ProductHero может быть серверным, а только carousel — клиентским.
- Импорты в клиентских компонентах — нет ли там того, что должно быть на сервере.

## РАЗДЕЛ 5. АНИМАЦИИ И ХЕВИ-БИБЛИОТЕКИ

У вас Framer Motion + GSAP + Lenis + Three.js. Это много для одного сайта.

- Three.js — где используется, грузится ли только на нужных страницах через `dynamic import`. Three.js это +400-600 KB.
- GSAP — используется параллельно с Framer Motion? Можно ли оставить только что-то одно.
- Lenis — нужен на всех страницах или только на главной/Hero. Если везде — можно ленивее.
- `prefers-reduced-motion` — все анимации респектят его?

## РАЗДЕЛ 6. РЕНДЕРИНГ И РЕАКТИВНОСТЬ

- React DevTools Profiler — пройди по 3-5 ключевым страницам, посмотри лишние ререндеры.
- `useEffect` без массива зависимостей — ищи в коде, такие штуки выполняются на каждый ререндер.
- `useMemo` / `useCallback` — где переборщили (премат оптимизация без замера) и где не хватает (списки на 50+ айтемов без мемоизации).
- Огромные массивы данных (галереи, продукты) — рендерятся целиком или виртуализируются?

## РАЗДЕЛ 7. ROUTING И ДАННЫЕ

- Все ли страницы — статические (○ Static) или SSG (●). Динамические `ƒ` — оправданы?
- `loading.tsx` есть на тяжёлых маршрутах?
- `generateStaticParams` для продуктовых страниц — должно генерить все 5 насосов / 8 модулей ИТП / 5 шкафов на этапе билда.
- `metadata` экспорты — везде ли есть, нет ли пустых.

## РАЗДЕЛ 8. CSS И TAILWIND

- `tailwind.config.ts` — `content` правильно настроен? Если содержит лишнее — JIT-компилятор медленнее.
- `globals.css` — нет ли там 200+ строк ручных стилей которые должны быть утилитами.
- Дубликаты классов в JSX — например, `flex flex-row items-center justify-center flex` (двойной flex).
- Inline-стили (`style={{...}}`) — где используются и почему не вынесены в Tailwind.

## РАЗДЕЛ 9. ОШИБКИ В КОНСОЛИ

- Открой production-сайт `anhel-website.vercel.app` в Chrome DevTools.
- Console: пройди по 5 ключевым страницам, собери все warnings и errors.
- Network: посмотри 404 на ассеты. Битые ссылки на сертификаты, фото, шрифты.
- Известные источники проблем: hydration mismatch, missing keys в списках, deprecated React API.

## РАЗДЕЛ 10. CORE WEB VITALS И LIGHTHOUSE

Объективные метрики Google. Запусти Lighthouse в Chrome DevTools на production-URL.

- 5 ключевых страниц: `/`, `/products/pumps/firefighting`, `/products/heating-unit`, `/products/control-systems/variable-frequency`, `/quiz/pumps`.
- Метрики: Performance, Accessibility, Best Practices, SEO. Отдельно — LCP, CLS, FID/INP, TBT.
- Mobile + Desktop отдельно.
- Что в красной зоне (<50) — приоритет 1. Жёлтое (50-90) — приоритет 2.

## РАЗДЕЛ 11. ЗАВИСИМОСТИ И БЕЗОПАСНОСТЬ

- `npm audit` — критические и высокие уязвимости.
- `npm outdated` — устаревшие пакеты, особенно `next`, `react`, `typescript`.
- Неиспользуемые зависимости — есть инструмент `depcheck`. Часто в `package.json` остаются библиотеки которые удалили из кода.
- `.env` файлы — нет ли утечки секретов в репозиторий (проверь `.gitignore`).

## РАЗДЕЛ 12. ГРЯЗЬ В РЕПО

- Файлы в `public/` которые не используются (старые временные ассеты, тестовые PDF).
- Закомментированный код в `src/`.
- `console.log` в production-сборке — поиск по коду.
- TODO / FIXME / HACK комментарии — список.
- Дубли компонентов с похожими именами (`Button.tsx`, `MyButton.tsx`, `CustomButton.tsx`).
- Папки `tmp/`, `_scripts/`, `outputs/` — что попадает в git, что должно быть в .gitignore.

## РАЗДЕЛ 13. TYPESCRIPT

- `npx tsc --noEmit` — exit 0 ожидается. Если ошибки — список.
- `any` в коде — поиск, список мест. `as` приведения тоже подсчёт.
- `// @ts-ignore` / `// @ts-expect-error` — почему стоят.

## РАЗДЕЛ 14. NEXT.JS-СПЕЦИФИКА

- `next.config.mjs` — `dangerouslyAllowSVG`, `images.remotePatterns`, `experimental` флаги. Что осталось от старых попыток.
- Middleware (`middleware.ts`) — есть ли, что делает, не запускается ли на каждом запросе впустую.
- API routes (`app/api/`) — все ли используются, нет ли осиротевших.
- Кеширование (`revalidate`, `dynamic = 'force-static'`) — настроено ли где надо.

## РАЗДЕЛ 15. SEO ТЕХНИЧЕСКИ

- `robots.txt` существует, корректный?
- `sitemap.xml` генерируется, включает все продуктовые страницы?
- `metadata` для всех страниц — `title`, `description`, `og:image`.
- `JSON-LD` (Product, Organization, BreadcrumbList) — где есть, где не хватает.
- Canonical URLs.

## РАЗДЕЛ 16. ОТЧЁТ — ФОРМАТ ДЛЯ НЕ-АЙТИШНИКА

Алексей не пишет код. Отчёт должен быть понятен ему без технического словаря. Каждая проблема описывается тремя колонками: «как сейчас» / «что делать» / «почему это важно по-человечески».

Файл: `_docs/internal_audit_<YYYY-MM-DD>.md`

### Правила формата

1. **Никаких голых терминов без расшифровки.** «LCP» = «время появления главной картинки на экране». «Bundle» = «размер скачиваемого кода». «Hydration» = «оживление страницы после загрузки».

2. **Колонка «почему это важно» — обязательна.** Без неё Алексей не сможет приоритизировать. Объяснять надо через бизнес-эффект: «клиент закроет вкладку», «выглядит несолидно», «на 4G грузится 6 секунд».

3. **Цифры везде где возможно.** «Грузится медленно» → «Грузится 4.2 секунды на 4G, должно 1.5».

4. **Сравнение с нормой.** «В норме до 200 КБ, у нас 480 КБ — в 2.4 раза больше».

5. **Усилие в часах/минутах**, не в стори-поинтах. «~30 минут», «~2 часа».

6. **Никаких списков из 50 пунктов.** Группируй похожие проблемы в одну строку. «Удалить 23 `console.log`» — одна строка, не 23.

Приоритеты:
- 🔴 высокий — клиент закрывает вкладку, выглядит сломано, заметно тормозит
- 🟡 средний — мелкие тормоза, вылезает в DevTools, не блокирует пользователя
- 🟢 низкий — косметика кода, отложить можно

## ПРАВИЛА

1. На разведке — НЕ ПРАВИШЬ ни строчки кода. Только метрики и анализ.
2. Не выдумывай проблемы где их нет. Если что-то спорно — пиши «возможно проблема» с пометкой «требует подтверждения».
3. Метрики — конкретные числа, не «медленно/быстро». «LCP 4.2s» а не «загружается долго».
4. После отчёта жди моего «ок» на каждую группу фиксов. Не атакуй сразу всё.

Начинай с раздела 1 (бандл), это даст быстрые цифры. Потом 10 (Lighthouse) — увидим где реально болит. Дальше последовательно.
